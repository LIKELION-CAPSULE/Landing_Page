# 투표 · 설문 · 사전예약 화면 검토

검토일: 2026-10-10. 대상: `/rooms`, `/survey`, `/preorder`, `/done`.

현재 포스터 중심 구성과 화면 흐름을 유지하면서 실제 제출 결과를 안내한다. 최신 `main`의 Supabase·Mixpanel 연결을 병합했으며, 저장 규격은 [프론트 연동 스키마](frontend-schema.md)를 따른다. 아래의 최초 검토·계약 제안은 연결 이전의 기록이다.

최초 검토 이후 프런트엔드 보완과 Supabase 연결에 맞춘 문구 변경을 반영했다.

## 반영한 보완 (2026-10-10)

- 공통: 뒤로가기와 같은 줄의 세 단계 진행 표시, 경로 전환 후 제목 포커스·뒤로 이동 시 기존 동작 포커스 복귀, 글자 크기 하한·줄바꿈·주요 동작의 44px 터치 영역, 보라색 버튼·placeholder·약관의 대비 보완.
- `/rooms`: 1개 선택 안내, 포스터 체크 배지, 기존 선택으로 계속하기를 제공한다. 9개 포스터의 모서리는 9 디자인 px로 통일했다. 실제 고유 방문자 수를 표시하며, 첫 요청의 로딩·실패와 마지막 집계 캐시를 처리한다. 포스터 확대·축소와 상세 카드의 제목 생략을 유지한다. 상세가 열릴 때 카드로 포커스를 보내 모바일 닫기 버튼의 자동 포커스 테두리를 없앴으며, 키보드 Tab으로 닫기 버튼에 이동하면 포커스 표시를 유지한다.
- `/survey`: 첫 항목 제목 우측의 `복수 선택 가능`, `다음: 사전예약`, 넓은 건너뛰기, 자유 입력 500자 제한·카운터. 후속 요청에 따라 선택사항 설명과 선택 칩의 체크·체크용 여백은 제거하고, 채움색으로 선택을 구분한다. 아무 답이 없어도 다음 단계로 이동한다. 건너뛴 상태를 별도로 기록하고 초안은 유지한다.
- `/preorder`: 선택한 룸·변경 링크, 이메일, 약관 동의만 표시한다. 후속 요청에 따라 설문 응답 요약과 나이대·공부 방식·기타 입력을 제거했으며 초안 타입과 수집 항목도 정리했다. 이메일·동의를 상위 상태에 보관해 페이지를 오가도 유지한다. 필수/선택 표시와 이메일·룸·동의 오류 안내, 첫 오류 포커스, 처리 중 중복 제출 방지, 실패 후 재시도를 제공한다. 설문 응답과 건너뛰기 상태는 별도의 설문 초안에 보관한다.
- `/done`: 저장 성공 후 **사전예약 완료**를 표시한다. 중복 이메일은 이미 예약한 주소라는 안내와 기존 예약이 변경되지 않았다는 설명을 표시하며, 새로 선택한 룸이 저장됐다고 보여주지 않는다. 직접 접속·새로고침 시 완료 정보를 확인할 수 없음을 안내하고, 이미 접수된 예약은 유지된다고 설명한다. 기존 예약 수정 API가 없으므로 다시 입력하는 링크는 `다른 이메일로 사전예약하기`로 바꿨다.
- `/preorder`의 미연결 안내를 제거하고 버튼을 `사전예약하기`·`사전예약 접수 중…`·`다시 시도하기`로 바꿨다. 실패 시 초안을 유지하고 완료로 이동하지 않는다. 환경변수 누락에 따른 `disabled`도 완료로 취급하지 않는다. 건너뛴 설문 초안은 보관하되 서버에 전송하지 않는다. 이메일과 응답은 브라우저 저장소에 보관하지 않는다.
- 조선시대 포스터 투표를 위한 후속 마이그레이션 `2026-10-12_joseon_room.sql`을 준비했다. 기존 백도준 투표를 유지하면서 `joseon` 허용값과 집계 뷰를 추가한다. 운영 DB 적용은 별도다.

### 보완 후 검증

최신 main 병합과 저장 결과 문구 변경 후:

- `npm run build`, `npm run lint`, `git diff --check` 통과. 기존 포스터 원본·배포 에셋과 약관 전문은 병합 전 파일과 바이트 단위로 비교해 보존을 확인했다.
- Chrome·WebKit 각각 320/402/1280px와 320px·글자 크기 200%에서 포스터 9개의 동일한 모서리, 카드로 초기 포커스, 키보드 닫기 버튼 포커스 표시, Escape 후 원래 포스터 복귀, 새 포스터 선택→설문→예약→완료를 확인했다. 가로 넘침과 JS 런타임 오류는 없었다. 실제 휴대폰의 카카오톡 브라우저는 별도 확인 대상이다.
- 임시 PostgreSQL(PGlite)에 기존 마이그레이션과 새 포스터 SQL을 적용해 실제 INSERT·UNIQUE 중복·집계·RLS를 확인했다. 백도준 과거 투표가 보존되고 조선시대 투표가 허용·집계되며, 새 SQL을 반복 적용해도 같은 결과였다.
- 로컬 REST 서버로 지연 중 중복 제출 차단, 저장 실패 후 입력 보존·재시도, 중복 이메일 시 기존 룸 불변, 건너뛴 설문 미전송, 환경변수 누락 시 완료 진입 차단을 확인했다. 잘못된 집계(null·음수·소수)는 0명으로 표시하지 않는다.
- 현재 공개 연결의 `landing_vote_total()`은 운영 환경에서 HTTP 200 응답을 받아 실제 숫자를 표시했다. 이 확인에서는 쓰기 요청을 차단했으며 운영 투표·예약 데이터를 생성하지 않았다. 새 포스터 SQL의 운영 DB 적용은 관리자에게 맡긴다.

## 범위와 근거

## Supabase 저장 방식 제안

공개키는 접속하는 앱을 식별하는 수단이고, 저장할 테이블·컬럼이나 사용자별 권한을 정의하지 않는다. 브라우저는 publishable 키 또는 기존 `anon` 키를 사용할 수 있지만 secret/`service_role` 키는 서버에만 둔다. 키와 함께 프로젝트 URL과 저장 API 계약을 받아야 한다. [Supabase API keys](https://supabase.com/docs/guides/getting-started/api-keys)

`JSONB` 컬럼 하나에 설문 묶음을 저장하는 방식은 가능하다. 그래도 테이블, 허용 필드, 자료형, 필수값, 길이 제한, 권한은 먼저 정해야 한다. 기존 조직 프로젝트에 임의 테이블을 만들거나 화면 상태를 그대로 전송하는 방식은 권하지 않는다.

### 기본안: 최종 예약 시 한 번 제출

1. 룸 선택과 설문은 공통 초안 상태에 보관한다.
2. 최종 화면에서 이메일과 필수 동의를 확인한다.
3. 룸·설문·예약·동의를 하나의 정해진 payload로 제출한다.
4. 백엔드가 검증하고 저장한 성공 응답을 받은 다음 `/done`을 표시한다.

이 방식에서는 예약을 마치지 않은 사용자의 투표와 설문은 DB에 남지 않는다. **이탈한 사용자의 응답도 집계하려면** 앞 단계의 별도 저장과 최종 예약 연결 식별자를 설계해야 한다. `N명`이 전체 투표자 수인지 예약 완료자 수인지도 이 결정에 따라 달라진다.

다음은 협의용 필드 예시이며, 현재 Supabase 스키마나 실제로 호출할 수 있는 API가 아니다.

```json
{
  "schema_version": 1,
  "idempotency_key": "<예약 시도별 UUID, 같은 제출 재시도에는 재사용>",
  "room_id": "smile",
  "email": "person@example.com",
  "survey": {
    "status": "answered",
    "picks": {
      "relation": ["선배"],
      "personality": ["다정함"],
      "world": ["학교·캠퍼스"]
    },
    "wish": ""
  },
  "consents": {
    "privacy": true,
    "marketing": false,
    "privacy_version": "<확정한 문서 버전>",
    "marketing_version": "<확정한 문서 버전>"
  }
}
```

- 현재 옵션은 한국어 라벨을 상태값으로 사용한다. 예시도 현재 값을 표시했으며, 운영 저장에는 백엔드와 합의한 고정 옵션 코드를 사용하면 문구 변경에 유리하다. 현재 룸 ID는 `smile`, `lantern`, `top`, `fenesis`, `cat`, `iljin`, `jurassic`, `lab`, `joseon`이다. 기존 백도준 포스터는 일진 포스터로 교체하고 `iljin` 항목 하나로 통합했으며, 조선시대 야간 학습 포스터를 새로 추가했다. 백엔드 ID와 같다고 가정하지 않는다.
- 설문의 `picks`는 현재 `Set`이다. 그대로 JSON 직렬화하면 배열이 되지 않으므로 전송 전에 `Array.from` 등으로 변환한다.
- 현재 건너뛰기는 설문 초안의 `status = "skipped"`로 구별하며 응답 초안도 유지한다. 저장 시 건너뛴 응답을 제외할지도 백엔드와 합의한다.
- 현재 UI는 제출 시 룸 선택을 필수로 검사한다. 백엔드에서도 룸의 필수 여부와 허용 ID를 확인한다. 나이대·공부 방식은 현재 입력·전송 대상에서 제외했다.
- 예약 ID·저장 시각·접수 시각은 서버가 생성한다. 동의 문서 버전을 허용 목록과 대조하고, 동의를 포함한 제출을 접수한 시각을 서버에서 기록한다.
- 간단한 초기는 예약 테이블 한 곳에 연락처·룸·동의를 명시적인 컬럼으로 두고 설문을 버전이 있는 JSONB로 묶을 수 있다. 여러 테이블로 나누면 부분 저장을 막기 위해 서버가 한 트랜잭션으로 처리한다. 최종 구조는 운영 백엔드와 맞춘다.

### 권한과 중복 처리

브라우저가 테이블에 직접 저장한다면 테이블 권한과 RLS 정책을 함께 정해야 한다. 로그인 없는 제출의 허용 범위를 제한하고, 연락처·개별 응답의 공개 조회/수정/삭제는 허용하지 않는 구성을 기본으로 협의한다. 서버 함수로 접수하는 구조라면 DB 직접 접근을 열지 않고 해당 함수에서 입력과 호출 권한을 검증할 수 있다. [Supabase Data API security](https://supabase.com/docs/guides/api/securing-your-api)

같은 요청 재시도는 idempotency key로, 같은 이메일의 재예약은 별도 정책과 DB 제약으로 처리한다. 중복이면 거절할지 기존 예약으로 안내할지, 투표 변경을 허용할지 합의한다. 다른 사람의 이메일을 입력한 클라이언트가 기존 예약을 덮어쓰도록 단순 공개 `upsert`하지 않는다. 공개키나 로컬 저장소만으로 실제 사람당 1표를 보장할 수는 없다.

RLS 자체는 요청 횟수를 제한하지 않는다. 공개 접수 경로의 반복 요청 방지는 서버의 요청 제한과 필요 시 추가 검증으로 별도 설계한다. [Supabase request checks](https://supabase.com/docs/guides/api/securing-your-api#pre-request-checks)

Vite 연동 시 `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY` 같은 이름을 사용할 수 있다. `VITE_*` 값은 브라우저 빌드에 노출되므로 공개키만 넣고 서버 비밀키는 넣지 않는다. 현재 코드는 환경변수를 사용하지 않아 로컬 화면 확인에는 `.env`가 필요하지 않다. [Vite env variables](https://vite.dev/guide/env-and-mode#env-variables)

## 검증

- 별도 headless Chrome에서 320/402/1280px × 네 화면의 스크린샷과 요소 경계를 확인했다. 12개 기본 화면에 가로 넘침이 없었다. 선택한 룸이 있는 정상 흐름의 완료 화면도 확인했다.
- 재현: 첫 포스터에 키보드 Enter → 상세 투표 → 설문 Space 선택·자유 입력 → 다음. 새 경로에서 포커스는 `BODY`였다.
- 재현: 예약 이메일·나이·공부 방식·필수 동의 입력 → 뒤로 → 설문 답변 유지 → 다시 예약. 예약 입력 네 항목 모두 초기화됐다.
- 잘못된 이메일은 제출 비활성화만 발생했다. 연결된 오류 설명과 `aria-invalid`가 없었다. 유효한 이메일과 필수 동의만으로 제출 가능했고 선택 항목은 생략할 수 있었다.
- 정상 흐름 제출 후 완료가 표시됐으나 Supabase/API 요청은 **0건**이었다. 직접 `/done` 진입과 완료 화면 새로고침에서도 완료가 표시됐고 선택 포스터는 비었다.
- 약관은 키보드 Enter로 열고 Escape로 닫을 수 있었고, 포커스가 원래 보기 버튼으로 복귀했다. 모션 감소 설정에서 약관 닫기는 애니메이션 없이 처리됐다. 현재 포스터 확대 연출은 유지할 만하다.
- 계산된 글자색·배경색으로 sRGB 대비를 산출했다. 반투명 placeholder는 실제 `#292929` 배경과 합성했다. 선택 칩은 선택 전후 배경의 명도 차이가 크므로 색상만으로 의미를 표현한다는 위반으로 분류하지 않았다. 체크 추가는 선택을 더 쉽게 파악하기 위한 개선 제안이다. [WCAG 1.4.1의 명도 차이 설명](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)

## 판정

최초 검토는 실제 저장 확인·완료 진입·버튼 문구·대비 문제로 운영 배포 기준 **Block**이었다.

후속 보완한 **프런트엔드 범위는 Approve**: 확인한 화면과 상태의 문구·대비·입력 보존·복구 동작을 반영했다. 실제 사전예약 운영은 저장 API·권한·서버 성공 응답·집계·확정 문구 연결 후 검증해야 한다. Supabase와 실제 기기 화면낭독기·Safari·브라우저 자체 줌은 이 판정 범위에 포함되지 않는다.
